# RBAC สำหรับร้านบ่อตกกุ้ง

## ผลตรวจระบบเดิม

ตรวจโค้ดที่ `9240e04` และอ่าน metadata ของ Supabase Production ระบบเก็บผู้ใช้ด้วยคีย์ `(shop_id, uid)` อยู่แล้ว คอลัมน์ `role` และ `status` เป็นข้อความ ตรวจพบ Admin และ Customer ที่เปิดใช้งาน ฐานข้อมูลมี RLS บนตารางหลักและไม่มี policy ใน schema public ขณะตรวจ แต่ตารางหลักบางตัวยังมี grants ให้ anon/authenticated ซึ่งการย้ายครั้งนี้ถอนออก พบ grant อนุมัติสมาชิกแบบเดิมหนึ่งรายการที่มีบทบาทร้านรองรับอยู่แล้ว เก็บตารางและข้อมูลเดิมไว้

| บทบาท | ก่อนปรับ | หลังปรับ |
| --- | --- | --- |
| Admin | ใช้ Admin Panel เดิม และเปลี่ยนบทบาทผ่าน API เขียน users ทั่วไป | ใช้หน้าเดิม เพิ่มรายชื่อและประวัติ เปลี่ยนบทบาท/สถานะผ่านธุรกรรมที่ป้องกันการลดสิทธิ์ Admin คนสุดท้าย |
| Cashier | ยังไม่มีบทบาท | แดชบอร์ดเดิมตามสิทธิ์ จัดการโต๊ะ สมาชิกผ่านคิว รายงาน และแนะนำลูกค้า |
| Operator | ใช้ Admin Panel ได้บางส่วน API ยังอนุญาตเขียนยอดและอนุมัติ Wallet | จัดการงานภายในโต๊ะ แสดง QR ลงบิลโต๊ะ รับเงินตามยอดค้าง และเปิด Player ของตน |
| Promoter | หน้าแนะนำอ่านและเขียนตารางตรง และ Player จำกัดการลงบิล | หน้าแนะนำที่ยืนยันสิทธิ์ตามร้าน ลิงก์/QR/Flex ของตนเอง และ Player ของตน |
| Customer | Player และประวัติตามสมาชิก | Player และประวัติของตน พร้อมการปฏิเสธเส้นทางหลังบ้านและหน้าแนะนำ |
| Platform Superadmin | ตรวจ platform grant แยก | ใช้ grant เดิมสำหรับงาน Platform และคงความเข้ากันได้กับบทบาทร้าน Superadmin เดิม |

Cashier ดูคิวปกติและอนุมัติรับเงินสดหรือถอนที่ผ่านขั้นตอนยืนยันใน LINE ได้ สลิปตรวจมือ การคืน/แปลงค่าคอม การปรับยอดสมาชิก และยกเลิกบิลใช้สิทธิ์ Admin การอ่านค่าระยะเวลาเปิดรอบใช้ประกอบงานเปิดรอบตามเดิม

## ขอบเขตที่แก้

- `admin.html` และ `admin-api-client.js` ใช้หน้าเดิม เพิ่มมุมมองตามบทบาท จัดการสิทธิ์และประวัติ และเรียกคำสั่งการเงินเฉพาะงาน
- `index.html`, `promoter.html`, `backer.html`, `dashboard.html`, `shop-create.html` และ `staging/member-apply.html` ตรวจการเปิดหน้า ใช้ API ของร้าน และเชื่อมรหัสแนะนำกับใบสมัคร หน้าจอ MC เดิมยังใช้รหัสผ่านแยกตามร้าน
- `admin-api`, `member-approval`, `round-notice`, `shop-login-check`, `shop-payments`, `wallet-topup`, `verify-slip` ตรวจตัวตน LINE และสิทธิ์เฉพาะร้านตามเส้นทางที่เกี่ยวข้อง `platform-billing`, `shop-referrals` และ `mc-board` ตรวจสอบแล้วและยังใช้การคุมสิทธิ์เดิม
- Migration ใช้ `users` เป็นแหล่งบทบาท เพิ่มตารางประวัติสิทธิ์และรายการปฏิบัติการ ถอนสิทธิ์ตาราง/ฟังก์ชันภายในจากไคลเอนต์ และย้ายการยกเลิกบิล ปรับยอด และตัดผลเข้าธุรกรรมเดียว การรัน migration ไม่อัปเดตแถวสมาชิกหรือยอดคงเหลือ
- Backer ยังเปิดดูทุนและประวัติได้ ฝากถอนผ่านแบบฟอร์ม Wallet ที่ตรวจสลิปและยืนยันถอนผ่าน LINE ยอดทุน Backer ใช้คอลัมน์เดิมเมื่ออนุมัติหรือเติมจากสลิป การแชร์ Flex ใช้ตัวเลือกผู้รับของ LINE LIFF และจะแสดงเมื่อ LIFF รองรับ
- ร้านที่เคยให้สิทธิ์ผ่าน `membership_admins` อย่างเดียวควรตรวจเทียบก่อน rollout และกำหนด Cashier/Admin อย่างตั้งใจ เพราะคิวสมาชิกใช้บทบาทใน `users` ชุดเดียวกับหลังบ้าน ผลตรวจ Production แบบอ่านอย่างเดียวพบศูนย์รายการที่ไม่มีบทบาทรองรับ ณ เวลาที่ตรวจ

- ตรวจพบ `notify-topup` และ `verify-slip` ใน Production เพิ่มเติมจาก source เดิมใน repo จึงนำเส้นทางทั้งสองมาอยู่ใน PR ด้วย `notify-topup` รับเฉพาะ webhook ที่ยืนยัน secret ของฐานข้อมูล และโหลดรายการจริงตามร้านก่อนส่ง LINE ส่วน `verify-slip` จำกัดสิทธิ์ดูรายการและตรวจบัญชีรับเงินตามร้าน
- ตั้ง `shop_internal_webhook.endpoint` ของแถว `notify-topup` เป็น URL ของ Edge Function ใน project ที่กำลังเผยแพร่ และเปิด pg_net ตามระบบเดิม Migration เริ่มต้นด้วย URL ว่าง จึงส่งออกจาก staging ได้เมื่อกำหนด URL ของ staging เองเท่านั้น

## Rollout และ rollback

1. ใช้ staging แยกและสำรอง schema/grants/นิยามฟังก์ชันก่อนเปลี่ยน ตรวจ Admin อย่างน้อยหนึ่งรายต่อร้านและตรวจผู้รับสิทธิ์คิวแบบเดิม
2. ทดลอง migration และ Edge Functions ใน staging จากนั้นเผยแพร่เว็บ staging ชุดเดียวกัน ตรวจ LINE LIFF ทั้งสอง channel, share target picker, QR โต๊ะ, คิวถอน, สลิป Thunder, รายการซ้ำ, payout และจอ MC ด้วยบัญชีทดสอบแยกร้าน
3. หากผ่านและมีคำสั่งเผยแพร่ ให้หยุดรับคำสั่งเขียนระหว่างเปลี่ยนเวอร์ชัน แล้วใช้ migration, deploy Edge Functions ที่แก้ ตั้ง URL webhook ของ project นี้ และเผยแพร่เว็บเป็นชุดเดียว การแยกเผยแพร่อาจทำให้หน้าเดิมเรียก RPC คนละเวอร์ชัน
4. หากต้องย้อน ให้หยุดการเขียน ย้อน Edge Functions/เว็บและ restore นิยามฟังก์ชันเดิมจาก commit ก่อนหน้า รวมถึง ACL จาก snapshot เฉพาะที่จำเป็น โดยเก็บตาราง audit และข้อมูลใหม่ไว้ อย่า restore snapshot ทับยอดหรือธุรกรรมที่บันทึกหลังเปิดใช้งาน ตรวจบัญชี Cashier ที่ตั้งหลัง rollout เพราะแอปรุ่นเดิมไม่รู้จักบทบาทนี้ก่อนเปิดใช้งานอีกครั้ง

รายการที่ต้องยืนยันใน staging ได้แก่ การเปิด LIFF ในมือถือจริง การเลือกผู้รับและส่ง Flex, การส่งข้อความยืนยันถอน, ผล Thunder จริง, คิวรายงาน และการทดสอบสองธุรกรรมพร้อมกันบน PostgreSQL เต็มรูปแบบ
